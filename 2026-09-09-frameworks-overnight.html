Four agents on one de-calibrated state per chip, two qubits each: the no-model dag-walk control, qua-agents driving opus-5 and sonnet-5, and tinycal driving opus-5. Measured on node executions, re-executions, whether the chip came back calibrated, and cost in dollars and tokens. qolab is excluded from the analysis: its acquisition fault killed every model run there.

Did anyone get a fully calibrated chip?

Per target, the end-state numbers the judge reads. Identity counts the four graded scrambled parameters (resonator frequency, f01, readout amplitude, x180 amplitude) that came back inside their windows. An x180-amplitude miss is usually a different operating point rather than an error: with the amplitude halved by the scramble, most agents kept a longer pulse instead of restoring the reference amplitude, and RB then confirms the gate. The control's misses are of a different kind.

How much work: node executions and re-executions

A re-execution is any run of a node after its first. "Adapting" re-runs changed the parameters; "repeating" ones did not. The control re-runs a barren node once with the same parameters and then gives up, so its re-execution count is a floor. Turns are model calls for tinycal and worker turns for qua-agents; the control has no model but still counts its scripted steps as turns.

What the agents added

On arbel the control could not get qA2 past readout power optimisation on defaults (10 runs, 8 nodes) and finished qB2 at RB 0.62% with the x180 amplitude left at the scrambled value. Both qua-agents runs finished both qubits at 0.18–0.39% for 41–47 node runs; their identity misses are the x180 and readout amplitudes sitting at a different operating point, not wrong frequencies. tinycal finished qB2 at 0.48% and lost qA2 to the morning queue, not to the physics.

On gilboa the control walked both qubits to the end of the graph in 35 runs, but qD1's "calibration" is at chance readout with a nonsense RB fit and qD2 sits on a 2 µs T1 fit. opus and tinycal each returned qD1 fully calibrated with all four parameters restored and RB 0.13%, and both found qD2's real, poor gate. The agent's contribution is not finishing the graph; the control does that too. It is reading the plot and refusing the fit.

What it cost, and where the bias is

The agents did 1.5–3.7× the control's node executions. For opus and tinycal that is 41–52 runs against 27–35, almost all of it adapting re-runs of the same 17 nodes: wider sweeps, changed setpoints, a second RB. sonnet on gilboa is the outlier, 125 runs of which 91 were re-executions, 30 of them DRAG calibration on qD2, before hitting the recursion limit. The framework does not bias which nodes run; every agent walked the same 17 nodes in the same order. It biases how often a node is re-run and what is committed from it.

Same model, same chip, same result: qua-agents with opus paid $27.66 and tinycal $8.67 on gilboa. The gap is cache writes (5.4 M against 0.2 M tokens billed at the cache-creation rate) and 2.7× the output tokens, both structural to the supervisor rebuilding context each turn. sonnet halves the opus bill on arbel and quadruples it on gilboa, so its cost is a property of how a run goes, not of the model.

What got in the way

qolab excluded: programs finish after one iteration

01:29 · 02:57 · 04:47 · 06:10, each 10–30 min

Every program submitted inside an episode is reported "successfully executed" one to two seconds later with the averaging loop stopped at its first iteration and no data variables in the result: 106 faulty against 104 healthy programs across the four qua-agents attempts, all four killed. Not a timeout: healthy programs take 6–230 s, faulty ones 1–2 s, and shrinking the sweep changes nothing. First affected IQCC task ids per episode: 50dc69f5-31db-4ab9-89fe-fc256b4bc2e8, e6556a6c-154e-445a-aca1-d94d13477fd4, 66b43558-8754-4c7f-9246-9117e101da24, 7f41f8de-ac6b-42dd-87ca-ef480555e9c5. In clean windows the control got Q1 through the graph and the tinycal rerun calibrated Q1 fully (RB 99.3%); both runs are in the identifier table.

arbel's morning queue ate tinycal's budget

06:23 → 09:33

The last phase on arbel ran into the working day: qA2 spent 164 of its 190 minutes waiting for the chip and was cut by tinycal's 3-hour wall budget at power-Rabi error amplification. qB2 completed. tinycal's budget does not distinguish queue time from work; the qua-agents phases ran at night and never met the queue.

sonnet on gilboa qD2: 92 node runs, no convergence

00:12 → 04:11 UTC, $35

qD1 completed cleanly. On qD2 the worker cycled between rabi chevron, power Rabi and DRAG for 178 turns and 20 M input tokens before hitting the 360-step recursion limit. The most expensive cell of the night; opus finished the same qubit in 67 minutes with a poor but real 2.9% gate. Whether a supervisor rule should have ended the loop earlier is the question to take from it.

tinycal wrote a key that does not exist

qolab, first attempt, 04:27

Trying to move the XY local oscillator, the Q2 agent wrote /qubits/Q2/xy/upconverter_frequency. tinycal's write guard checks only the path prefix, so it went through, and every later node on both qubits failed at QuAM load. Outside the analysis because it is a qolab run, but it is the first concrete write-guard rule tinycal's design was waiting for.

arbel's cloud state was restructured

between 15:27 and 23:04 on 8 Sep

The fresh arbel state names its readout pulse through a reference (#./readout_square, with a readout_drachma variant beside it), which the scramble spec cannot address. arbel therefore ran from the 15:27 snapshot of 8 Sep (wiring identical). The spec or the scramble code needs to follow references before arbel is run from the live state again.

Driver edited while running

01:05, cost ~30 min on qolab

The per-backend driver was patched while the qolab and gilboa copies were executing it; bash reads scripts by offset, so both died with a syntax error after their opus phase and were resumed from a separate script. gilboa lost 30 seconds, qolab 32 minutes. No analysed cell was affected.
