qua-agents and tinycal, side by side

The two agent frameworks the benchmark runs against the same qua-libs nodes and the same IQCC backends. First how one turn works in each — what the model is shown, what it may decide, and what stands between its call and the chip. Then the runtime that surrounds that turn. Read from the checkouts of 21 Sep 2026: qua-agents 61209cf (integration), tinycal 1125d0c (main).

How a turn works

Both frameworks run the same ReAct turn against the same nodes, so the comparison that matters is not the box count but where each one puts the decisions. Strip the HTTP API, console, read model and persistence and the decision machinery is about 9.5k lines in qua-agents against about 1.1k in tinycal — the ratio barely moves, because the complexity is in the deciding, not the plumbing. The two drawings below share a skeleton: see the turn, decide, pass the gate, measure, record, return.

1what the model sees 2who picks the next measurement 3who decides what reaches the device 4what stops a doom loop 5where per-node knowledge lives

The markers sit where each decision is actually taken. In qua-agents they are spread across four layers of machinery; in tinycal three of them collapse into the model box. That is the whole difference: qua-agents spends its complexity deciding what the model may know and may do, tinycal spends almost none and lets the model decide. What that choice costs or buys is measured in the side-by-side report.

Where a calibration decision is taken

A different question from the one above, and the one that decides how a run is debugged and tuned: when the agent picks a node, a sweep range or a value to write, how many places did that come from? Each row below is somewhere a person can change what happens to a qubit. What matters is not only the count but the kind — whether the model can override it or not.

Each tag names what that source takes out of the model’s hands. Everything else a source contributes — the node’s prose, a checklist, the graph’s presets, the objective — is advice the model may ignore. A recipe’s write_value_bounds is not advice: it reaches the control surface, and an out-of-bounds write is rejected outright.

The asymmetry is sharper than the count. In tinycal nothing outside the model chooses which node runs next, with which parameters, or whether a value is written — the four sources shape the advice and fence the writable paths, and that is all. In qua-agents five distinct mechanisms reach inside that decision — the graph’s edges, the plan overlay’s pruning, the parameter bounds, the pending-state gate and the escalation thresholds — authored across six of the nine sources.

The runtime around the turn

The same two frameworks on five infrastructure rows — launch, agent turn, gate, hardware, record and state. This is where the 12× size difference lives, and much of it is accessory to the comparison above: swap the SQLite ledger for files, or drop the HTTP API and console, and the agent behaves the same on the chip. Note that each box here is drawn the same size regardless of what is behind it — GuardedExecutionService is twelve modules, the write_state guard is about two hundred lines.

What both share

  • The same calibration content: the qua-libs fork's 1Q node scripts run through QUAlibrate, with the node's own fit and proposed updates captured without being applied. tinycal reads the node set and presets from the same bring-up graph file qua-agents traverses, and ignores its edges.
  • The same hardware path: jobs go to the IQCC cloud, which queues them itself; neither framework serialises node runs locally.
  • The same device state file: state.json under QuAM, shared by all agents on a backend. qua-agents commits by compare-and-swap in SharedQuamStore; tinycal holds a file lock and commits to git.
  • The same benchmark contract: both produce the usage fields the judge prices (input_tokens, output_tokens, cache read and write, reasoning) per model turn, and node executions with target, node, parameters, status and numerics; project_tinycal.py maps tinycal's events.jsonl onto the document schema the qua-agents projection produces.
